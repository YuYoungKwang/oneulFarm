# oneulFarm 최종발표 대본

## 0. 문서 전제

- 이 문서는 `데모 시연 제외`, `본 발표 10~12분` 기준으로 작성한다.
- 발표 대상은 교수님과 평가자이며, 톤은 `공식적 설명형`으로 유지한다.
- 목표는 기능을 많이 나열하는 것이 아니라, `왜 이 서비스를 만들었고`, `어떤 구조로 구현했으며`, `무엇을 검증했는지`를 논리적으로 전달하는 것이다.

## 1. 이번 발표의 핵심 프레이밍

발표 전체에서 아래 네 문장을 일관되게 유지한다.

1. oneulFarm은 `단순 시세 조회 서비스`가 아니라 `시세 데이터를 근거로 레시피와 구매를 연결하는 농산물 커머스`다.
2. 이 프로젝트의 핵심 사용자 흐름은 `메인 추천 또는 AI 식단 생성 -> 재료 확인 -> 구매 -> 주문/절약 확인`이다.
3. 운영 구조는 `게시판형 직거래`가 아니라 `플랫폼 직매입·소분 판매` 방식이다.
4. `식단 AI/챗봇`은 사용자 맞춤 식단 생성과 재료 구매 연결을 담당하는 `핵심 기능`이며, 발표에서는 `현재 구현 범위`와 `향후 고도화 범위`를 구분해서 설명한다.

## 3. 전체 발표 대본

### 3.1 표지

안녕하세요. 저는 oneulFarm 팀 발표를 맡게 된 이찬희입니다.
이번 프로젝트는 `농산물 가격 추이 시세 정보 분석 기반의 농산물 직거래 시스템`을 주제로 진행했고, 저희는 이를 `시세 기반 레시피 재료 판매 e커머스`라는 방향으로 구체화했습니다.

오늘 발표에서는 먼저 프로젝트가 어떤 문제의식에서 출발했는지 설명드리고, 이후 시스템 구조와 핵심 기능, 그리고 마지막으로 검증 결과까지 순서대로 말씀드리겠습니다.

### 3.2 프로젝트 개요와 방향 변화

먼저 프로젝트 개요입니다.

저희 팀은 처음에는 `시세 분석 상품 추천 e커머스`에 더 가까운 방향에서 출발했습니다.  
하지만 기획 발표 피드백을 통해, 시세 분석 기능이 많아도 사용자 입장에서는 이 서비스가 어떤 가치를 주는지 한눈에 드러나지 않는다는 점을 확인했습니다.

그래서 중간 발표 단계에서는 방향을 `시세 기반 레시피 재료 e커머스`로 재정의했습니다.  
즉, 가격 정보를 보여주는 것에서 그치지 않고, 사용자가 `무엇을 살지`, `그 재료로 무엇을 만들지`, `어떻게 구매로 이어질지`까지 연결하는 구조로 바꾼 것입니다.

최종적으로는 여기에 `레시피를 중심으로 재료 구매가 이어지는 사용 경험`과 `AI 기반 맞춤 식단 생성 기능`까지 더해, 단순 가격 비교가 아니라 `농산물 소비 경험 전체를 설계하는 서비스`로 정리했습니다.

### 3.3 주제 선택 이유, 목적, 목표, 특징

저희가 이 주제를 선택한 이유는 실제 식재료 구매 과정에서 소비자가 가격 정보를 따로 확인해야 하고, 또 기존 식재료 구매 서비스에서는 재료를 판매하는 데 집중하는 경우가 많아 `구매 이후 활용`까지는 충분히 연결되지 않는다고 느꼈기 때문입니다.

특히 농산물은 시세 변동이 크기 때문에, 가격 정보를 반영한 상품 추천이 가능하다면 소비자는 더 합리적인 소비를 할 수 있습니다.  
또 여기에 레시피를 연결하면, 사용자는 단순히 상품만 보는 것이 아니라 `이 재료로 어떤 식사를 할 수 있는지`까지 함께 판단할 수 있습니다.

정리하면 저희 서비스의 목적은 세 가지입니다.  
첫째, 공공 시세 데이터를 실제 구매 판단에 연결해 합리적인 농산물 소비를 돕는 것입니다.  
둘째, 레시피를 통해 재료 활용 방법을 제안하고, 이를 구매 전환까지 이어지게 만드는 것입니다.
셋째, AI를 통해 사용자 상황에 맞는 식단을 생성하고, 필요한 재료를 실제 구매 흐름과 연결하는 것입니다.

그래서 목표 역시 `시세 비교가 가능한 농산물 커머스를 구현하는 것`, `레시피를 상품과 연결해 구매로 이어지게 하는 것`, 그리고 `AI 챗봇을 활용해 맞춤 식단 생성과 재료 구매 연결까지 제공하는 것`으로 설정했습니다.

### 3.4 팀 소개

다음은 팀 소개입니다.

프로젝트는 역할 기반으로 분담했습니다.  
메인 페이지와 공통 레이아웃, 기획 발표는 박상문 팀원이 맡았고,  
상품과 주문 기능, 관리자 페이지, 최종 통합은 허륜 팀장이 담당했습니다.  
시세 분석과 레시피, GitHub 관리는 유영광 팀원이 맡았고,  
로그인과 회원가입, 관리자 페이지 일부는 백종진 팀원이 담당했습니다.  
마이페이지와 주문 관리, 최종 발표 정리는 이찬희 팀원이 맡았습니다.

발표에서는 이 역할 분담이 이후 일정과 요구사항 분석, 구현 결과와 자연스럽게 이어진다는 점을 함께 보시면 됩니다.

### 3.5 사용 기술 및 개발 환경

사용 기술은 프론트엔드에서 `HTML, CSS, JavaScript, React`,  
백엔드에서 `Java, Spring, MyBatis`,  
데이터베이스는 `Oracle`을 사용했습니다.

개발 도구는 VS Code와 Eclipse, 서버는 Apache Tomcat, 형상 관리는 Git과 GitHub를 사용했습니다.

이 조합을 선택한 이유는 프론트와 백의 역할을 명확히 나누고, 주문, 상품, 시세, 관리자 기능처럼 데이터 구조가 분명한 프로젝트를 안정적으로 구현하기에 적합했기 때문입니다.

### 3.6 시스템 아키텍처

아키텍처는 `React 프론트엔드`, `Spring API 서버`, `Oracle 데이터베이스`의 3계층 구조로 설계했습니다.

여기에 외부 데이터와 서비스 연동이 붙습니다.  
시세 데이터는 `KAMIS`, 레시피 데이터는 `식품안전나라 공공 API`, 인기 키워드는 `네이버 데이터랩`을 활용했습니다.  
또 결제는 `PortOne`, 로그인은 `Google, Kakao, Naver OAuth` 확장 구조를 고려했고, 메일 기능은 SMTP 기반으로 설계했습니다.

중요한 점은 외부 데이터를 단순 조회로만 쓰지 않았다는 것입니다.  
시세 데이터는 상품과 직접 비교되어 `평균가`, `가격 차이`, `절약률` 계산에 활용되고, 레시피 데이터는 상품 추천 및 장바구니 흐름과 연결됩니다.

여기에 `OpenAI API`는 맞춤 식단 생성 기능에 활용했습니다.  
사용자가 건강 상태나 식단 조건을 입력하면, AI가 기간별 식단과 통합 재료 목록을 구성하고, 서버는 이를 다시 판매 중인 상품과 매칭해 `구매 가능한 재료`, `장바구니 후보`, `캘린더 저장` 흐름으로 연결합니다.

즉 AI는 단순한 부가 기능이 아니라, oneulFarm에서 `개인화된 식사 계획을 실제 구매 행동으로 연결하는 핵심 축`이라고 말씀드릴 수 있습니다.

### 3.7 프로젝트 일정

프로젝트는 약 한 달 동안 진행했고,  
`기획/설계 -> 컴포넌트 개발 -> 로직 고도화 -> 안정화/테스트 -> 최종 발표` 순서로 진행했습니다.

이 과정에서 중요한 점은 기능을 병렬로 많이 만드는 것보다,  
각자 맡은 기능을 하나의 사용자 흐름으로 연결되게 만드는 것이었습니다.

예를 들어 시세 분석은 별도 페이지로 끝나지 않고 상품 비교와 대시보드에 연결되어야 했고,  
레시피 역시 조회 기능이 아니라 장바구니와 주문 흐름으로 이어져야 했기 때문에, 일정 역시 이 연결성을 중심으로 배분했습니다.

### 3.8 역할별 일정과 구현 포인트

역할별로 보면,

박상문 팀원은 요구사항 정의와 프로젝트 거버넌스, 그리고 메인 UI 방향을 정리했습니다.  
백종진 팀원은 Oracle DB 구조와 보안 인증 레이어, 관리자 재고 관리 구조를 담당했습니다.  
유영광 팀원은 KAMIS 실시간 연동과 가격 변동 분석, 재료-레시피-상품 매핑 로직을 맡았습니다.  
허륜 팀장은 상품 탐색, 주문, 결제 흐름과 전체 프론트 통합을 담당했습니다.  
이찬희 팀원은 구매 행동 분석, 절약 리포트, 발표 전략 정리를 담당했습니다.

즉, 일정표는 단순 작업 목록이 아니라 `메인 경험`, `데이터 처리`, `운영 구조`, `가치 시각화`를 나누어 책임을 분담한 결과라고 보시면 됩니다.

### 3.9 요구사항 분석의 기준

이제 요구사항 분석입니다.

저희는 요구사항을 크게 `사용자 서비스`, `추천과 분석`, `운영 기능` 세 축으로 나눴습니다.

사용자 서비스에서는 메인페이지, 회원, 상품, 주문 기능을 기본 축으로 두었습니다.  
추천과 분석 영역에서는 시세 분석, 레시피, 추천, 대시보드 기능을 추가했습니다.  
운영 기능에서는 관리자 화면을 통해 매입, 소분, 재고, 주문, 사용자 관리를 다룰 수 있도록 설계했습니다.

이렇게 나눈 이유는 이 프로젝트가 단순 쇼핑몰도 아니고, 단순 분석 대시보드도 아니기 때문입니다.  
`실제 구매가 일어나는 커머스`, `구매를 돕는 데이터`, `실제로 운영 가능한 관리자 구조`가 모두 있어야 프로젝트가 완성되기 때문입니다.

### 3.10 사용자 기능 핵심 요약

사용자 기능을 먼저 보면, 메인페이지에서는 배너 슬라이드와 추천 농산물, 평균가 이하 상품을 강조하도록 했습니다.  
회원 기능은 회원가입, 로그인, 로그인 유지, 계정 복구, 약관 동의까지 기본적인 사용자 관리 흐름을 포함합니다.

시세 분석 기능은 KAMIS API 기반으로 가격 데이터를 수집하고 저장한 뒤, 이동평균, 가격 변동률, 평균가 비교를 시각화하도록 했습니다.  
상품 기능은 목록, 검색, 필터, 상세 조회, 장바구니, 관련 레시피 연결까지 포함했습니다.  
주문 기능은 장바구니 조회, 수정, 삭제, 주문 생성, 배송 상태 관리로 이어집니다.

즉, 사용자 입장에서는 `들어오고`, `탐색하고`, `비교하고`, `구매하고`, `사후 확인하는` 흐름이 모두 하나의 서비스 안에서 닫히도록 설계했습니다.

### 3.11 레시피, 추천, 마이페이지, 대시보드, 관리자

다음으로 이 프로젝트를 차별화하는 기능들입니다.

레시피는 공공 API에서 데이터를 수집해 조회만 제공하는 것이 아니라,  
재료 기반 검색이 가능하고, 레시피 상세에서 필요한 농산물을 바로 추천해 장바구니로 연결되도록 설계했습니다.

추천 기능은 평균가 이하 상품, 구매 적기 상품, 제철 상품, 인기 농산물, 그리고 레시피 매칭 결과를 함께 반영합니다.  
실제 코드에서도 메인 추천은 `제철 상품`, `연결 레시피`, `네이버 데이터랩 기반 인기 키워드`를 조합해서 생성하도록 구현되어 있습니다.

AI 식단 기능은 사용자가 건강 상태, 목표, 기간을 입력하면 맞춤 식단을 생성하고,  
식단 전체에 필요한 재료를 통합한 뒤 판매 중인 상품과 자동으로 매칭해 `구매 가능한 재료`와 `구매 불가능한 재료`를 구분해서 보여주도록 구현했습니다.  
또 매칭된 재료는 장바구니 후보와 예상 금액으로 이어지고, 원하면 마이페이지 식단 캘린더로 가져와 저장할 수 있습니다.

마이페이지에서는 프로필, 배송지, 주문 내역, 찜, 리뷰를 관리할 수 있고,  
대시보드에서는 `누적 절약 금액`, `월별 절약 금액`, `품목별 절약 분석`, `자주 구매한 상품`, `최근 구매 상품`을 볼 수 있게 했습니다.

관리자 기능은 이 서비스가 게시판형 거래가 아니라 `플랫폼 직매입·소분 판매` 구조라는 점 때문에 특히 중요합니다.  
관리자는 매입 등록, 소분 처리, 상품 등록, 주문 상태 관리, 사용자 관리까지 할 수 있어야 실제 운영 흐름이 성립합니다.

### 3.12 기능별 상세 역할 정리

구체적으로 보면 박상문 팀원이 담당한 메인 페이지와 공통 레이아웃은  
고정 네비게이션, 메인 배너, 추천 상품, 공통 이동 구조를 중심으로 설계되었습니다.

허륜 팀장이 담당한 상품 서비스는 목록, 검색, 필터, 상세, 장바구니, 주문, 결제 흐름을 중심으로 구현되었고,  
AI 식단 기능은 맞춤 식단 생성 결과를 판매 상품과 연결해 장바구니 후보를 제안하고, 식단 관리 화면까지 이어지도록 구성했습니다.

이찬희 팀원이 담당한 마이페이지와 배송 관리는 프로필, 주문 내역, 리뷰, 배송 정보 관리에 초점을 두었고,  
백종진 팀원이 맡은 로그인과 관리자 페이지는 상품/재고 관리, 주문/배송 관리, 사용자 관리, 통계 집계를 담당합니다.

유영광 팀원이 담당한 레시피 서비스는 공공 API 기반 레시피 수집, 재료 기반 검색, 레시피 상세 내 상품 추천, 그리고 `레시피 재료 한 번에 담기` 흐름으로 연결됩니다.

### 3.13 메뉴 트리

메뉴 트리는 사용자 사이트와 관리자 사이트를 분리해서 설계했습니다.

사용자 사이트는 `홈, 가격 분석, 상품, 레시피, 맞춤 식단 AI, 마이페이지`로 구성했고,  
관리자 사이트는 `관리자 대시보드, 상품 관리, 매입/소분 관리, 주문 관리, 회원 관리, 콘텐츠 관리`로 구성했습니다.

이 구조의 장점은 사용자 화면에서는 구매와 탐색에 집중하고,  
관리자 화면에서는 운영과 상태 관리를 분리해서 볼 수 있다는 점입니다.

또 발표 관점에서는 메뉴 트리를 통해 프로젝트가 단순 UI 묶음이 아니라, `도메인별로 분리된 서비스 구조`를 갖고 있다는 점을 보여줄 수 있습니다.

### 3.14 ERD와 테이블 설계

다음은 ERD와 핵심 테이블 구조입니다.

주요 테이블은 `회원`, `상품`, `시세 정보`, `시세-상품 매칭`, `주문 정보`, `주문 상품`, `레시피`로 구성했습니다.

여기서 중요한 테이블은 두 개입니다.

첫째는 `PRICE_SNAPSHOT`과 `PRODUCT_PRICE_MATCH`입니다.  
시세 원본 데이터를 저장하고, 이를 상품과 연결해 가격 차이와 절약률을 계산합니다.

둘째는 `ORDER_ITEM`입니다.  
이 테이블에는 단순히 주문 수량과 단가만 저장하는 것이 아니라, `주문 시점 평균가`, `실제 구매 단가`, `절약 금액`을 함께 저장합니다.

이 구조를 선택한 이유는 나중에 시세가 변하더라도 사용자가 구매했던 시점의 절약 가치를 다시 계산하고 재현할 수 있어야 하기 때문입니다.  
즉, 대시보드의 절약 리포트는 단순 화면 계산이 아니라 데이터 모델에서부터 뒷받침되도록 설계했습니다.

### 3.15 사용자 시나리오

사용자 시나리오는 크게 구매 사용자와 관리자 흐름으로 나누어 볼 수 있습니다.

구매 사용자는 메인페이지에서 진입한 뒤 레시피를 선택하고, 장바구니에 재료를 담고, 구매와 결제를 진행합니다.  
이후 주문 관리와 배송 확인, 리뷰 작성까지 이어집니다.

관리자는 주문이 들어오면 주문을 확인하고 상태를 변경하며, 취소 요청이나 배송 진행 상태도 관리합니다.

이 유스케이스에서 보여주고 싶었던 핵심은 `레시피가 콘텐츠로 끝나지 않고 실제 구매 전환의 시작점이 된다`는 점입니다.  
즉, 이 프로젝트의 중심은 상품 나열이 아니라 `활용 맥락이 있는 구매`입니다.

### 3.16 AI 챗봇 DFD

다음은 AI 챗봇 DFD입니다.

이 부분은 현재 구현한 AI 식단 흐름을 정리한 슬라이드입니다.  
사용자가 건강 상태나 기간을 입력하면 OpenAI 기반으로 식단 응답을 생성하고, 이를 일자별 식단과 통합 재료 목록으로 구조화합니다.  
그 다음 서버에서 판매 중인 상품과 다시 매칭해서 `구매 가능한 재료`, `장바구니 후보`, `예상 금액`까지 보여주고, 필요하면 마이페이지 식단 캘린더로 저장할 수 있도록 했습니다.

다만 발표에서는 AI를 만능 기능처럼 표현하기보다,  
`개인화된 식단 제안과 구매 연결을 돕는 핵심 인터페이스`라고 설명하고, 향후에는 구매 이력과 선호도까지 반영하는 방향으로 고도화할 수 있다고 덧붙이는 것이 가장 자연스럽습니다.

### 3.17 테스트 시나리오

핵심 기능은 대표 테스트 케이스로 검증했습니다.

첫 번째는 `상품-시세 매칭 재계산 후 평균가 비교 갱신`입니다.  
시세가 새로 수집되면 상품 화면의 평균가 비교 정보와 절약률, 배지 상태가 정상 반영되는지를 확인했습니다.

두 번째는 `재료 정리에서 구매 가능한 재료 시각 구분`입니다.  
레시피 상세에서 구매 가능한 재료와 그렇지 않은 재료가 구분되어 보이고, 구매 가능한 항목은 실제 상품 상세로 연결되는지 확인했습니다.

세 번째는 `레시피 그룹형 장바구니 저장`입니다.  
레시피에서 여러 재료를 선택했을 때 개별 상품이 아니라 `레시피 그룹` 단위로 장바구니에 저장되고, 구성 상품과 수량, 예상 절약 금액이 함께 보이는지를 확인했습니다.

이 테스트는 이 프로젝트의 핵심이 `시세 데이터`, `레시피 매핑`, `구매 전환`의 연결이라는 점을 검증하는 사례라고 보시면 됩니다.

### 3.18 마무리

마지막으로 정리하겠습니다.

oneulFarm은 단순히 농산물 가격을 보여주는 서비스가 아니라,  
`시세 데이터를 근거로 농산물을 추천하고`,  
`그 재료로 만들 수 있는 레시피를 연결하고`,  
`AI를 통해 사용자 맞춤 식단을 제안하고`,  
`실제 구매와 주문, 그리고 구매 후 절약 확인까지 이어지게 만든 농산물 커머스`입니다.

또 운영 구조 측면에서는 플랫폼 직매입·소분 판매 방식을 채택해 현실적인 관리자 흐름까지 함께 설계했고,  
데이터 측면에서는 주문 시점 평균가와 절약 금액을 저장해 단순 쇼핑몰을 넘어서 `데이터 제품 성격을 가진 커머스`로 확장할 수 있는 기반을 만들었습니다.

이번 프로젝트를 통해 저희는 기능을 많이 넣는 것보다, 사용자 문제 정의와 핵심 가치 정리가 더 중요하다는 점을 배웠습니다.  
이상으로 발표를 마치겠습니다.

## 5. 예상 질문과 답변

### Q1. 이 프로젝트의 핵심은 시세 분석인가요, 레시피 커머스인가요?

시세 분석 자체가 핵심이라기보다, `시세 데이터를 근거로 레시피와 구매를 연결하는 커머스 구조`가 핵심입니다.  
시세 분석은 사용자의 구매 판단을 돕는 근거 데이터이고, 메인 사용자 흐름은 레시피 기반 구매 전환입니다.

### Q2. 발표 제목에는 직거래 시스템이라고 되어 있는데, 실제 구현은 어떤 구조인가요?

발표에서 말하는 직거래는 유통 단계를 줄인다는 방향성을 의미합니다.  
실제 구현은 생산자-소비자 게시판형 거래가 아니라, `플랫폼이 직접 매입하고 소분해서 판매하는 B2C 구조`입니다.  
이 방식이 MVP 단계에서 더 현실적이고 운영 가능성이 높다고 판단했습니다.

### Q3. 시세 데이터와 판매 단위가 다르면 어떻게 비교했나요?

상품 단위와 시세 단위를 그대로 비교하면 왜곡이 생기기 때문에,  
kg, g, 개수 단위를 정규화하고 필요한 경우 표준 중량 기준으로 환산해 비교하도록 설계했습니다.  
그 결과 상품별 `비교 기준 가격`, `가격 차이`, `절약률`을 계산할 수 있습니다.

### Q4. 절약 금액은 어떻게 계산했나요?

기본 식은 `(주문 시점 평균 시세 - 실제 구매 단가) x 구매 수량`입니다.  
그리고 이 값을 주문 상품 단위로 저장해서, 이후 시세가 바뀌더라도 당시 절약 금액을 그대로 보여줄 수 있게 했습니다.

### Q5. 레시피와 상품 연결은 어떤 방식으로 구현했나요?

기본적으로는 레시피 재료명과 판매 중인 상품명을 토큰 기준으로 정규화해 매칭합니다.  
추가로 대표 키워드, 검색 별칭, 허용 레시피 카테고리 매핑 테이블을 두어 추천 정확도를 보완했습니다.

### Q6. 왜 대시보드가 중요한가요?

이 프로젝트의 차별점은 구매 전 시세 비교뿐 아니라, 구매 후에도 사용자가 `얼마나 절약했는지`를 확인할 수 있다는 점입니다.  
대시보드는 누적 절약 금액, 월별 절약 흐름, 자주 구매한 상품을 보여주면서 재구매와 만족도를 높이는 역할을 합니다.

### Q7. 관리자 기능을 왜 별도로 강조했나요?

이 서비스는 플랫폼 직매입·소분 판매 구조이기 때문에, 사용자 기능만 있어서는 완성되지 않습니다.  
실제 운영을 위해서는 매입 등록, 소분 이력, 재고 관리, 주문 상태 변경이 함께 있어야 서비스가 돌아갑니다.

### Q8. AI 챗봇은 실제 구현되었나요?

네, 현재 맞춤 식단 생성과 재료 통합, 판매 중인 상품 매칭, 장바구니 후보 제안, 식단 캘린더 저장 흐름까지 구현했습니다.  
다만 구매 이력과 선호도까지 반영하는 더 정교한 초개인화 추천은 향후 고도화 범위라고 설명드리는 것이 정확합니다.

### Q9. 외부 API는 어떤 것을 사용했나요?

시세 데이터는 `KAMIS`, 레시피는 `식품안전나라 공공 API`, 인기 키워드는 `네이버 데이터랩`, 맞춤 식단 생성은 `OpenAI API`를 사용했습니다.  
결제는 PortOne 연동 구조를 고려했고, 로그인은 OAuth 확장 구조를 설계했습니다.

### Q10. 일반 쇼핑몰과 비교했을 때 차별점은 무엇인가요?

일반 쇼핑몰은 상품 탐색이 중심이지만, oneulFarm은 `가격 근거`, `레시피 활용`, `AI 맞춤 식단`, `구매 후 절약 리포트`를 한 흐름으로 연결합니다.  
즉, 단순 판매가 아니라 `구매 이유를 데이터로 설명하는 커머스`라는 점이 차별점입니다.

### Q11. 왜 React, Spring, Oracle 조합을 선택했나요?

프론트와 백엔드를 명확히 분리하고, 상품/주문/시세/통계처럼 구조화된 데이터를 안정적으로 다루기 위해서입니다.  
특히 Oracle과 MyBatis 조합은 테이블 중심 설계와 쿼리 제어에 적합하다고 판단했습니다.

### Q12. 테스트는 어떤 기준으로 진행했나요?

핵심 연결 고리를 기준으로 테스트했습니다.  
즉 `시세 매칭이 정상 갱신되는지`, `레시피에서 구매 가능한 재료가 구분되는지`, `레시피 단위 장바구니 구성이 제대로 저장되는지`, 그리고 `AI 식단 생성 후 재료 매칭과 캘린더 저장 흐름이 이어지는지`를 대표 시나리오로 검증했습니다.

## 6. 발표 시 표현 주의

- `직거래 시스템`이라고만 말하지 말고, 반드시 `플랫폼 직매입·소분 판매 구조`라고 바로 보완해서 설명한다.
- AI는 `실제 구현한 핵심 기능`으로 설명하되, `현재 구현 범위`와 `향후 고도화 범위`를 구분해서 말한다.
- `시세 분석 서비스`라고 소개하지 말고, `시세 데이터를 근거로 레시피와 구매를 연결한 커머스`라고 설명한다.
- 기능을 나열할 때는 항상 `왜 필요한 기능인지`까지 붙여서 말한다.

## 7. 발표 직전 한 줄 요약

oneulFarm은 `공공 시세 데이터`, `레시피 활용`, `AI 맞춤 식단`, `구매 전환`, `구매 후 절약 리포트`를 하나로 연결한 농산물 커머스 프로젝트입니다.
