# oneulFarm 예상 질문과 답변

## 1. 답변 원칙
- 길게 설명하지 말고 먼저 결론부터 말한다.
- 없는 기능을 있는 것처럼 말하지 않는다.
- 질문이 기술적이어도 다시 사용자 가치와 연결해서 마무리한다.
- 팀 발표에서는 `저희 팀은`으로 답하고, 개인 기여가 필요한 경우 마지막에 덧붙인다.

## 2. 핵심 질문

### Q1. oneulFarm은 일반 농산물 쇼핑몰과 무엇이 다른가요?
저희 서비스의 가장 큰 차별점은 공공 시세 데이터를 실제 구매 판단에 연결했다는 점입니다.

일반 쇼핑몰은 가격만 보여주는 경우가 많지만, oneulFarm은 평균 시세와 절약률, 절약 금액까지 함께 보여주고, 구매 후에는 대시보드로 체감하게 만들었습니다.

### Q2. 왜 굳이 시세 데이터를 연결했나요?
농산물은 가격 변동성이 커서 사용자가 가격 적정성을 판단하기 어렵기 때문입니다.

저희 팀은 공개된 시세 정보를 상품 화면과 연결하면 사용자가 더 합리적으로 구매할 수 있다고 봤습니다.

### Q3. 절약 금액은 어떻게 계산하나요?
기본 기준은 `주문 시점 평균 시세 - 실제 구매 단가`에 구매 수량을 곱하는 방식입니다.

즉 주문 당시 데이터를 함께 저장해서, 나중에 시세가 바뀌어도 당시 절약 기준이 흔들리지 않도록 설계했습니다.

### Q4. 왜 대시보드까지 만들었나요?
시세 비교만 보여주면 구매 직전 판단에서 끝나기 때문입니다.

저희 팀은 사용자가 실제로 얼마나 절약했는지 누적해서 체감해야 서비스 가치를 더 분명하게 느낄 수 있다고 판단했습니다.

### Q5. 관리자 화면은 왜 필요한가요?
이 서비스는 사용자 화면만 좋아 보여서는 완성되지 않기 때문입니다.

매입, 소분, 상품 관리, 주문 관리를 실제 운영 흐름으로 연결해야 사용자 화면의 가격 정보와 상품 정보가 신뢰를 갖게 됩니다.

### Q5-1. 레시피 기능은 왜 넣었나요?
저희 팀은 농산물 구매가 결제로 끝나면 서비스 체류와 재방문 이유가 약해진다고 봤습니다.

그래서 레시피를 단순 읽을거리로 두지 않고, 재료 검색과 연관 상품 연결까지 포함해 구매 후 활용과 재구매를 돕는 기능으로 넣었습니다.

### Q6. 시세 데이터는 어떤 식으로 들어오나요?
공공 시세 데이터를 수집해서 `PRICE_SNAPSHOT`에 저장하고, 이를 상품 정보와 매칭해서 사용자 화면에 노출합니다.

즉 외부 데이터가 그대로 끝나는 것이 아니라 서비스 내부 데이터 모델로 흡수되어 재사용됩니다.

### Q7. 기술 스택은 왜 이렇게 선택했나요?
프론트엔드는 React로 화면 상태를 유연하게 다루기 좋았고, 백엔드는 Spring MVC와 MyBatis로 도메인별 API와 SQL 제어를 명확하게 가져갈 수 있었습니다.

Oracle은 관계형 데이터와 집계, 운영 데이터 관리에 적합하다고 판단했습니다.

### Q8. 인증과 보안은 어떻게 처리했나요?
사용자 인증은 JWT 기반 구조를 사용했습니다.

계정, 주문, 배송지, 리뷰, 대시보드처럼 사용자 데이터가 필요한 API는 인증 상태를 바탕으로 분리해 관리했습니다.

### Q9. 가장 어려웠던 구현 포인트는 무엇인가요?
저희 팀 기준에서는 시세 데이터, 상품 데이터, 주문 데이터, 대시보드 집계를 각각 따로 두지 않고 하나의 흐름으로 연결하는 부분이 가장 중요했고도 어려운 지점이었습니다.

단순 조회 기능보다 데이터 간 기준 시점을 맞추는 설계가 더 중요했습니다.

### Q10. 발표에서 보여준 기능은 전부 실제 연동인가요?
핵심 사용자 기능과 관리자 기능은 실제 API 연동 범위가 넓습니다.

다만 외부 환경 영향을 받을 수 있는 결제나 일부 외부 응답 구간은 발표 안정성을 위해 설명 중심으로 보완하고 있습니다.

### Q11. 현재 한계는 무엇인가요?
발표 기준 현재 구조는 핵심 흐름 구현에 집중되어 있어서, 향후에는 추천 정교화, 수요 예측, 관리자 권한 체계 강화, 운영 자동화가 더 필요합니다.

즉 기반 구조는 갖췄고, 다음 단계는 고도화입니다.

### Q12. 확장 방향은 무엇인가요?
시세 기반 구매 추천 고도화, 사용자별 소비 패턴 기반 개인화, 운영 자동화, 예측형 분석으로 확장할 수 있습니다.

특히 저희 서비스는 이미 시세와 주문, 대시보드 데이터가 연결되어 있어서 확장 기반이 마련되어 있습니다.

레시피 영역도 향후에는 개인 구매 이력과 선호 재료를 반영한 개인화 콘텐츠로 확장할 수 있습니다.

## 3. 기술 질문 대응

### Q13. 왜 주문 시점 가격을 따로 저장하나요?
절약 금액 계산의 기준 시점을 고정하기 위해서입니다.

나중에 평균 시세가 바뀌어도 주문 당시 기준 절약 값이 달라지지 않게 하려는 목적입니다.

### Q14. 왜 관리자와 사용자 흐름을 함께 구현했나요?
저희 팀은 서비스가 실제로 어떻게 운영되는지까지 보여줘야 프로젝트 완성도가 올라간다고 판단했습니다.

그래서 사용자 경험과 운영 구조를 분리하지 않고 함께 설계했습니다.

### Q15. 왜 해시 라우팅 구조를 사용했나요?
현재 프로젝트 구조에서 빠르게 라우팅을 분리하고, 메인, 상품, 계정, 관리자 흐름을 명확하게 나누기 위한 선택이었습니다.

프로젝트 단계상 구현 속도와 구조 명확성을 우선했습니다.

## 4. 팀 발표용 보조 답변

### 팀 역할을 물어볼 때
저희 팀은 사용자 가치가 바로 보이는 흐름과 운영 구조가 함께 보이도록 역할을 나눠 개발했습니다.

프론트 화면 구성, 백엔드 API, 시세 연동, 관리자 운영, 마이페이지와 대시보드 같은 영역을 분담하면서도 최종 흐름은 하나로 맞췄습니다.

### 본인 기여를 따로 물어볼 때
제 담당 범위에서는 특히 마이페이지, 주문관리, 대시보드, 배송지, 리뷰처럼 구매 이후 사용자가 서비스를 체감하는 구간을 실제 API 기준으로 연결하는 데 집중했습니다.

또한 화면 분리와 데이터 흐름을 정리해서 유지보수성과 확장성도 함께 고려했습니다.
