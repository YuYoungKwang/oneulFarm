# 구현 계획

## 1. 문서 목적

이 문서는 `oneulFarm` 프로젝트에서 처음 합의했던 구현 순서와 이후 작업하면서 정리된 정책, 화면 구조, API 우선순위를 기록하는 계획 문서다.

이 문서에서 관리하는 내용:

- 어떤 기능을 어떤 순서로 구현할지
- 각 기능에서 어떤 화면 구조를 기준으로 잡을지
- 백엔드와 프론트를 어떤 방식으로 연결할지
- 더미 데이터와 테스트를 어떤 기준으로 준비할지
- 어떤 영역이 현재 담당 범위인지

운영 원칙:

- 실제 구현이 진행되면서 계획이 바뀌면 이 문서를 수정한다.
- 완료 여부 자체는 `progress.md`에서 관리하고, 이 문서는 “원래 어떤 기준으로 가기로 했는가”를 정리하는 데 집중한다.
- 구현 순서가 바뀌거나 담당 범위 판단이 바뀌면 반드시 기록한다.

## 2. 전체 구현 방향

프로젝트는 처음부터 모든 기능을 동시에 완성하는 방식이 아니라, 아래 순서로 점진적으로 구현하는 방향으로 잡았다.

1. 마이페이지 핵심 흐름 구현
2. 대시보드 요약 및 분석 영역 구현
3. 회원정보/배송지 관리 기능 보강
4. 리뷰/찜 등 미완료 개인화 영역 연결
5. 이후 필요 시 관리자/추가 분석 기능 확장

핵심 원칙:

- 먼저 화면에 보이는 흐름을 만든다.
- 그다음 더미 데이터를 실제 API로 교체한다.
- 마지막에 예외 처리, 정책, 세부 UX를 보강한다.

## 3. 담당 범위 기준

현재 작업은 주로 `마이페이지`, `대시보드`, `회원정보`, `배송지` 영역을 중심으로 진행한다.

현재 담당 범위로 본 영역:

- 주문 목록/주문 상세
- 대시보드 요약/분석
- 상세 개인정보
- 비밀번호 변경
- 배송지 관리
- 마이페이지 UI/UX 개선

현재 직접 구현 우선순위에서 뒤로 미룬 영역:

- 리뷰관리
- 찜한상품
- 상품 상세 페이지

판단 기준:

- 리뷰와 상품은 기능상 연결성이 높지만, 상품 상세 페이지 전체 구현은 현재 담당 범위 밖일 가능성이 크다고 판단했다.
- 따라서 리뷰는 필요성은 인정하되, 담당 범위를 다시 확인한 뒤 진행하기로 했다.

## 4. 화면 구조 계획

### 4.1 마이페이지

마이페이지는 관리형 개인 페이지로 정의한다.

기본 구조:

- 상단 프로필 요약 영역
- 하단 탭 영역
  - 주문내역
  - 찜한상품
  - 리뷰관리

세부 계획:

- 주문내역은 카드 목록 + 상세 보기 구조
- 주문 상세는 해당 주문 카드 바로 아래에서 열리는 방식
- 찜한상품은 카드 그리드형
- 리뷰관리는 `작성 가능한 리뷰`와 `내가 작성한 리뷰`의 2영역 구조
- 개인정보는 간략 카드 + 별도 상세 페이지 구조에서 시작했지만, 이후 `한 리스트 안에서 항목별 인라인 편집` 구조가 더 낫다고 판단해 계획을 수정했다.
- 배송지 관리는 별도 페이지보다 모달 구조를 유지하되, 목록 모드와 입력/수정 모드를 분리하는 쪽으로 정리했다.

### 4.2 대시보드

대시보드는 분석형 페이지로 정의한다.

구성 계획:

- 상단 KPI 카드 4개
- 중단 차트 영역 2개
  - 월별 절약 금액
  - 품목별 절약 분석
- 하단 패턴 영역
  - 평균 구매 단가
  - 절약률
  - 최다 구매 품목
  - 최근 구매 상품

구현 방향:

- 먼저 더미 데이터로 레이아웃 완성
- 이후 summary API부터 연결
- 마지막에 월별/품목별/패턴 API를 붙여 전체 실데이터로 교체

### 4.3 상세 개인정보 페이지

초기 방향:

- 표시 카드 / 수정 카드 / 비밀번호 변경 카드 분리

수정된 방향:

- 정보 목록을 한 번만 보여주는 페이지
- 각 항목 우측에 `수정` 또는 `변경` 버튼 배치
- 수정 가능한 항목만 인라인 편집

현재 계획 기준:

- 닉네임, 이메일, 연락처는 인라인 편집
- 비밀번호는 같은 목록 안에서 인라인 변경
- 회원번호 같은 내부 식별값은 사용자에게 노출하지 않음
- 기본 배송지는 읽기 전용으로 표시하고, 필요 시 배송지 관리 기능으로 이동

### 4.4 배송지 관리 모달

초기 방향:

- 목록과 추가 폼을 동시에 보여주는 구조

문제:

- 배송지가 늘어나면 모달이 길어지고 복잡해짐

수정된 방향:

- 기본은 목록 중심
- `배송지 추가`를 누르면 목록을 숨기고 입력 모드로 전환
- 수정도 별도 수정 모드로 처리
- 목록 영역은 고정 높이 + 내부 스크롤

추가 계획:

- 기본 배송지는 카드 자체로도 구분
- 삭제 전 확인
- 기본 배송지 해제 방지

## 5. 백엔드 구현 계획

### 5.1 공통 원칙

- Spring MVC + MyBatis 구조 유지
- Controller / Service / Dao / DTO 분리
- 가능하면 요청 DTO와 응답 DTO를 역할 기준으로 나눈다
- 같은 테이블을 보더라도 역할이 다르면 분리 유지
- 필드와 검증이 같은 요청은 통합 가능

### 5.2 주문

우선 구현 대상:

- 주문 목록 API
- 주문 상세 API

계획 포인트:

- 주문 목록은 대표 상품명, 상품 수, 총 절약 금액 계산 필요
- 주문 상세는 배송/결제/주문상품/리뷰 가능 여부까지 포함
- 리뷰 작성 가능 여부는 주문 상세 응답에서 계산

### 5.3 대시보드

우선 구현 대상:

- summary API
- monthly-savings API
- product-savings API
- patterns API

계획 포인트:

- summary로 먼저 화면 상단 KPI를 닫는다
- 나머지는 차트와 패턴 카드를 위한 집계 응답으로 분리

### 5.4 회원정보

구현 대상:

- 내 정보 조회
- 내 정보 수정
- 비밀번호 변경
- 이메일 중복 체크
- 닉네임 중복 체크

정책:

- 현재 로그인 체계가 완성되지 않았으므로 임시로 `X-USER-NO` 헤더를 사용
- 저장 전 중복 확인을 프론트에서도 요구

### 5.5 배송지

구현 대상:

- 배송지 목록 조회
- 배송지 추가
- 배송지 수정
- 기본 배송지 변경
- 배송지 삭제

정책:

- 기본 배송지는 항상 하나는 존재해야 함
- 배송지가 하나뿐이면 무조건 기본 배송지
- 현재 기본 배송지를 해제만 하는 수정은 불가
- 삭제 전 사용자 확인 필요

## 6. 프론트 구현 계획

### 6.1 구조

프론트는 페이지를 한 파일에 몰아넣기보다 기능 단위로 분리하는 방향으로 작업한다.

우선 분리 대상으로 본 것:

- `AccountApp`
- `MyPageView`
- `DashboardView`
- `ProfileDetailView`
- `OrderDetailPanel`
- `AddressModal`

원칙:

- 새 기능은 가능하면 별도 컴포넌트로 분리
- 공용성이 낮은 스타일은 해당 도메인 CSS에 넣기
- 계정/마이페이지 관련 스타일은 `styles/account.css`에 우선 배치

### 6.2 CSS 운영 계획

합의된 방향:

- 공용으로 재사용할 게 아니면 계정 화면 CSS는 `account.css`에 작성
- 너무 범용적인 클래스명은 피함
- 필요하면 도메인 기준 접두어를 붙여 충돌 가능성을 낮춤
- 다른 작업과 겹칠 수 있는 대형 공용 파일 수정은 최소화

### 6.3 인코딩 운영 계획

인코딩 깨짐이 반복되어 아래 기준을 도입했다.

- 전체 파일 저장 기준은 UTF-8
- 루트 `.editorconfig`로 저장 기준 고정
- `.vscode/settings.json`으로 VS Code 저장 인코딩 고정
- 이미 깨진 문서는 변환보다 재작성 우선

## 7. 더미 데이터 및 테스트 계획

### 7.1 주문 테스트 데이터

초기 목표:

- 주문내역 2건
- 배송완료 1건 / 배송중 1건
- 리뷰 존재 1건 / 리뷰 미작성 1건

추가 목표:

- 대시보드 테스트 강화를 위해 2026-01, 2026-02, 2026-03 주문 데이터 구성
- 감자를 최다 구매 품목으로 만들기
- 월별 절약 금액 차트가 3개월 이상 보이게 만들기

### 7.2 배송지 테스트 데이터

목표:

- 기본 배송지 1개
- 일반 배송지 여러 개
- 목록이 늘어났을 때 모달 레이아웃 확인
- 기본 배송지 수정/삭제 정책 확인

### 7.3 테스트 기준

주요 확인 대상:

- 주문 목록 응답 정렬 및 금액
- 주문 상세 응답 구조
- 대시보드 summary/차트/패턴 응답
- 회원정보 수정 반영 여부
- 비밀번호 변경 실패 메시지
- 배송지 추가/수정/삭제/기본 변경 정책

## 8. 진행 중 수정된 계획

처음 계획에서 변경된 대표 사항:

- 상세 개인정보는 카드 분리 구조에서 인라인 편집 구조로 변경
- 배송지 관리는 펼침형 입력 폼에서 목록/입력 모드 분리 구조로 변경
- 기본 배송지 정책을 더 강하게 제한하는 방향으로 보강
- 리뷰/상품은 우선순위를 뒤로 미루고, 현재 담당 범위를 마이페이지/대시보드/회원정보/배송지 중심으로 좁힘

## 9. 아직 미완료인 계획 항목

현재 계획상 남아 있는 대표 항목:

- 리뷰관리 실연동
- 찜한상품 실연동
- 상품 영역과의 연결 범위 재판단
- 문서 인코딩 전체 정리

## 10. 다음 작업 판단 기준

다음 작업을 잡을 때는 아래 순서로 판단한다.

1. 현재 담당 범위 안의 미완료 기능인지 확인
2. 이미 구현한 흐름을 닫는 작업인지 확인
3. 다른 사람 작업과 충돌 가능성이 낮은지 확인
4. 화면만 필요한 작업인지, 백엔드 연동이 필요한 작업인지 먼저 분리

현재 기준 우선 후보:

- 리뷰관리 실연동 여부 재판단
- 찜한상품 실데이터 연동 여부 검토
- 회원정보/배송지 UX 세부 보강
